## 这一版干什么

`-15` 已经把真凶按住（进程自抬 jetsam 上限），但**判据还是靠猜**：心跳里的
`rss` 是 `getrusage().Maxrss`，含干净的 file-backed 页，比内核记账的
footprint 大一倍左右。这一版把尺子换成和内核同一把。

### ① 心跳/启动改用 `ri_phys_footprint`

```
__proc_info(PROC_INFO_CALL_PIDRUSAGE=9, pid, RUSAGE_INFO_V0=0, 0, buf, 96)
  └ buf[16..]  struct rusage_info_v0
     32 ri_pkg_idle_wkups   40 ri_interrupt_wkups   64 ri_resident_size
     72 ri_phys_footprint   ← 内核 jetsam 记账的就是这个
```

输出：

```
[mem] footprint=?MB resident=?MB wkups=?（proc_info syscall）
[alive] pid=... rss=49MB fp=?MB wk=? goroutines=35
```

- `fp=` 与老大导出的 `launchctl procinfo` 里的 `physicalFootprint` 同口径。
- 取不到时自动退到 `launchctl procinfo`（每 5 分钟一次，只抓 `<key>physicalFootprint</key>`），
  日志会写「launchctl procinfo 兜底」。两条路都失败才只剩 `rss`。
- `wk=` 是累计 `ri_interrupt_wkups`，两次心跳相减即可算唤醒速率
  （18:10 那份 procinfo 是 `timerWakeups 1,373,901 / 24min ≈ 950 次/秒`）。

### ② JetsamEvent 真的能读出来了

`-15` 有两个 bug：`/var/mobile` 与 `/private/var/mobile` 是同一处，按目录字符串
去重导致同一个文件打两遍；只读前 96KB，`wb2api` 那段在后面，等于白读。

现在：按 basename 去重、上限 2MB、正文按 JSON 解析、递归找 `name` 命中 `wb2api`
的进程字典，打出 `reason / rpages / lifetimeMax / phys_footprint`。

### ③ CI 门禁同步

`verify patch wiring` 增加两条：`go logBootMemory()`、`fp=%dMB` 缺一即红。
（`-14` 就是「文件进包、main 没调用」，这一类必须由流水线挡。）

## 判据

```
[mem] footprint=24MB resident=37MB wkups=...（proc_info syscall）
```

- 这行出来了 = syscall 猜对了，以后判「内存有没有涨」看 `fp=`。
- 若写「launchctl procinfo 兜底」= `proc_info` 调用号不对，功能不受影响，
  下一版换回 syscall 再试。
- 稳态参考（`-15` 实测 34 分钟）：`rss 49MB / sys 38~39MB / footprint 24MB`，
  先爬后平，不是单调上升。
