## 修的是什么

`-16` 把「被列进内存快照」当成了「被杀」。真机日志：

```
[jetsam] JetsamEvent-2026-11-09-182356.ips → name=wb2api reason=<nil> rpages=1583 lifetimeMax=2138
```

`reason=<nil>` 不是「查不到」，而是**这条不是 victim**。JetsamEvent 会把内存最高的
几十个进程全抄一份，只有真正被杀的条目才带 `reason`（最早那份
`per-process-limit, rpages=1152` 就是 victim）。

这一错直接误导了排查：18:04 / 18:23 / 18:42 三次「wb2api 死因」其实是快照成员，
我们的进程当时活得好好的。

## 改法

1. **按 reason 分流**：`collectProcs()` 收集所有进程条目（有 `name` 且带 `pid`/`rpages`），
   带 `reason` 的才算被杀，最多列 4 条。
2. **我方单独一行**，明确标注：

```
[jetsam]   182356.ips 我方: rpages=1583 lifetimeMax=2138 footprint=<nil>（快照成员，未杀）keys=…
```

   如果真被杀，会写「被杀的就是我们」。
3. **打出 schema**：`keys=` 是该条目的键名（最多 14 个），事件顶层
   `reason=` / `largestProcess=` 也一并带出 —— 下次不用再猜字段叫什么。

## 顺带确认的两件事

- `proc_info(PROC_INFO_CALL_PIDRUSAGE)` 猜对了：真机打出
  `[mem] footprint=9MB resident=24MB wkups=141（proc_info syscall）`，
  与导出的 `launchctl procinfo` 里 `physicalFootprint` 同口径。
- `wk=` 可用：从 141 涨到 498858 用了 26m20s ≈ **316 次/秒** 中断唤醒，
  CPU 0.6%。不是热循环，但值得记一笔。
